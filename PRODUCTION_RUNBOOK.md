# MemoryVerse Production Runbook & Operational Guide

This runbook outlines operational procedures, disaster recovery protocols, performance mitigations, and incident response procedures for maintaining **MemoryVerse** in production.

---

## 1. Database Backup & Disaster Recovery

MemoryVerse utilizes a PostgreSQL relational database storing core schemas (`users`, `memories`, `journeys`, `sections`, `media`, `reactions`, `comments`, `places`).

### 1.1 Manual Database Backup (`pg_dump`)

Execute a custom-format compressed backup before deploying major migrations or on an automated schedule:

```bash
# Set credentials or pass via environment
export PGPASSWORD="<your_db_password>"
TIMESTAMP=$(date +"%Y%m%d_%H%M%S")

# Create compressed custom dump
pg_dump -h <DB_HOST> \
        -p <DB_PORT:-5432> \
        -U <DB_USER> \
        -d <DB_NAME:-memoryverse> \
        -F c \
        -b \
        -v \
        -f "memoryverse_backup_${TIMESTAMP}.dump"
```

**Flags Explained:**
- `-F c`: Custom PostgreSQL archive format (compressed, supports parallel restore and selective table restoration).
- `-b`: Include large objects (blobs).
- `-v`: Verbose output to monitor table-by-table progress.
- `-f`: Output filename.

### 1.2 Database Restoration (`pg_restore`)

To restore a backup into a fresh or existing database instance:

```bash
export PGPASSWORD="<your_db_password>"

# Clean existing objects and restore
pg_restore -h <DB_HOST> \
           -p <DB_PORT:-5432> \
           -U <DB_USER> \
           -d <DB_NAME:-memoryverse> \
           -v \
           --clean \
           --if-exists \
           "memoryverse_backup_<TIMESTAMP>.dump"
```

> **Warning:** `--clean` drops database objects before recreating them. Never run this against active production unless performing an authorized disaster restore.

## 2. Render Cold Start Mitigation (Service Liveness)

When hosted on Render Starter/Free tiers, backend web services spin down into hibernation after 15 minutes of inbound HTTP inactivity. The subsequent cold start can take 40–60 seconds, resulting in timeout errors or sluggish initial requests for users.

### 2.1 External Heartbeat Configuration (UptimeRobot)

Configure an automated external uptime monitor to send periodic HTTP pings:

1. **Service:** [UptimeRobot](https://uptimerobot.com) (Free Plan)
2. **Monitor Type:** `HTTP(s)`
3. **Friendly Name:** `MemoryVerse Backend Liveness`
4. **URL / IP:** `https://<YOUR_RENDER_BACKEND_URL>/api/health`
5. **Monitoring Interval:** `10 minutes` (prevents the 15-minute hibernation timeout)
6. **HTTP Method:** `GET`
7. **Expected Status Code:** `200 OK`

### 2.2 Alternative: GitHub Actions Scheduled Ping

If external SaaS monitors are restricted, deploy this lightweight GitHub Action (`.github/workflows/keep-alive.yml`):

```yaml
name: Production Keep-Alive Ping

on:
  schedule:
    - cron: '*/12 * * * *' # Triggers every 12 minutes
  workflow_dispatch:

jobs:
  ping:
    runs-on: ubuntu-latest
    steps:
      - name: Ping Backend Health
        run: |
          curl -s -f -m 30 "https://<YOUR_RENDER_BACKEND_URL>/api/health" || echo "Heartbeat ping failed"
```

## 3. Cloudinary Bandwidth Optimization & Quota Failover

MemoryVerse integrates Cloudinary for cloud media delivery and automated transformations.

### 3.1 Bandwidth Safeguards
- All image delivery URLs generated by `CloudinaryStorageService` use dynamic optimizations: `f_auto,q_auto,w_1200` to prevent uncompressed original images from exhausting monthly transfer caps.
- Thumbnails use low-bandwidth bounds: `c_fill,g_auto,w_400,h_400`.

### 3.2 Quota Exhaustion Emergency Protocol
If Cloudinary reaches 100% of its monthly bandwidth allowance (25 GB on free tier):

1. **Bypass Dynamic Transformations:**
   - In Cloudinary Console under **Settings > Security**, uncheck "Restricted Media Types".
   - Or configure the application to deliver standard un-transformed raw asset URLs.

2. **Switch to Local Storage Fallback:**
   - Change environment variable in your production deployment settings:
     ```env
     APP_STORAGE_PROVIDER=LOCAL
     APP_STORAGE_LOCAL_PATH=/var/data/memoryverse/uploads
     ```
   - All newly uploaded memories and avatars will be stored on local persistent disk rather than Cloudinary.

3. **Frontend Defensive Fallback:**
   - All frontend `<img>` elements utilize the `ImageFallbackDirective` (`mvFallback`). If any remote Cloudinary asset fails with HTTP 404 or 403, it degrades gracefully to a warm placeholder rather than showing broken image icons.

## 4. API Security & Rate Limiting Guidelines

Phase 5 introduced a sliding-window rate limiting filter (`RateLimitingFilter.java`) directly in the Spring Boot security pipeline.

### 4.1 Enforced Limits
| Route Pattern | Window | Threshold | Key Identifier |
| :--- | :--- | :--- | :--- |
| `POST /api/auth/**` | 60 seconds | 5 requests | Client IP Address |
| `POST /api/ai/**` | 60 seconds | 10 requests | User UUID (or IP if unauthenticated) |

### 4.2 Handling HTTP 429 Too Many Requests
- When an IP or user exceeds their threshold, the server rejects the request immediately with:
  - **HTTP Status:** `429 Too Many Requests`
  - **Header:** `Retry-After: 60`
  - **Payload:**
    ```json
    {
      "timestamp": "2026-09-07T20:00:00Z",
      "status": 429,
      "error": "Too Many Requests",
      "message": "Rate limit exceeded. Please wait a moment before trying again.",
      "path": "/api/auth/login"
    }
    ```
- The frontend `error.interceptor.ts` intercepts HTTP 429 and displays a non-intrusive warning snackbar: *"Too many requests. Please wait a moment before trying again."*

## 5. Security & Data Privacy Center

Located on the frontend under `/profile` (and aliased at `/settings`):

1. **Default Privacy Setting:**
   - Allows users to select their default privacy visibility:
     - `PRIVATE_TO_ME` (Personal, confidential)
     - `CIRCLE_COMPANIONS` (Circle members can view & contribute)
     - `PUBLIC_ARCHIVE` (Open access)
   - Persisted across authoring sessions.

2. **GDPR / CCPA Data Portability:**
   - Endpoint: `GET /api/export/archive`
   - Generates a full `.zip` bundle containing:
     - `profile.json`: User profile metadata.
     - `memories.json`: Structured array of authored memories.
     - `archive-summary.md`: Clean Markdown document detailing memories and timestamps.
     - `media-manifest.txt`: Complete catalog of all associated media assets and URLs.

3. **Account Deletion:**
   - Endpoint: `DELETE /api/users/me`
   - Strict confirmation requires the user to type `"DELETE"`.
   - If referenced in existing memories or shared circles, user details are scrubbed and anonymized (`"Former Member"`) to maintain referential integrity without storing personal identifiable information (PII).

## 6. Incident Checklist

| Symptom | Probable Cause | Action |
| :--- | :--- | :--- |
| `HTTP 502 / 504` on initial visit | Render web service cold start | Check UptimeRobot monitor; verify `/api/health` returns `200`. |
| `HTTP 429` on login or AI query | User/IP rate limit exceeded | Wait 60 seconds. If legitimate load, adjust thresholds in `RateLimitingFilter.java`. |
| `HTTP 404` on image assets | Media deleted or Cloudinary quota exceeded | Check Cloudinary dashboard; verify image fallback directive activates. |
| High database memory / connection spikes | Uncached aggregate queries | Ensure Redis caching is active (`CACHE_PLACES`, `CACHE_PEOPLE`, `CACHE_JOURNEYS`). |
